## Module 10 gap-closure: Microsoft Docs in unified search

Closes the one remaining gap `docs/TDD.md` had flagged in Module 10 (Semantic Search). Every earlier pass in this roadmap had treated Microsoft Docs as needing "a live-fetch integration this app doesn't have" and deliberately declined to fabricate one — the same standard this app's docs hold every other generation feature to. That premise was re-checked rather than repeated verbatim, and it turned out to be outdated: Microsoft runs its own official, unauthenticated MCP (Model Context Protocol) server for exactly this purpose, `https://learn.microsoft.com/api/mcp`, tool `microsoft_docs_search` — a real, sanctioned integration path, not a workaround. Confirmed real via web research (not assumed), then this sandbox's own `learn.microsoft.com` network egress was confirmed blocked (a direct fetch attempt returned `EGRESS_BLOCKED`) before deciding whether to build it — the decision to build anyway, unverified until it runs in production, was made explicitly with the user rather than silently either way.

- ✅ **New `src/lib/search/microsoft-docs.ts`** — `searchMicrosoftDocs(query)` opens a fresh `@modelcontextprotocol/sdk` `Client` + `StreamableHTTPClientTransport` per call (this runs inside a Vercel serverless invocation, not a long-lived process, so there's no connection worth pooling), calls the `microsoft_docs_search` tool with an 8s timeout, and returns `MicrosoftDocResult[] | null` — `null` means the live call itself failed (connect, call, timeout, or an unrecognized response shape), never thrown; `[]` means it succeeded and found nothing. Same null-vs-empty-array contract `trySemanticSearchEntries`/`trySemanticSearchScripts` already established in `src/lib/vault/search.ts`. The exact response shape couldn't be confirmed live from this sandbox, so `parseMicrosoftDocsSearchResult()` is deliberately defensive: it tries `structuredContent` first (if the tool declares an output schema), then falls back to regex-extracting `[title](url)` markdown links out of the plain-text `content` blocks MCP search tools return by convention when no schema is declared. The SDK's actual method signatures (`Client.connect`, `Client.callTool`, `CallToolResultSchema`'s shape) were confirmed by reading the installed package's own type definitions and bundled example client, not assumed from memory.
- ✅ **`microsoft-docs.test.ts`** — 7 unit tests against the pure parser, independent of any network call (the one part of this feature that actually could be verified before shipping): missing/malformed input → `[]`; structured-content success; entries missing a title or url are skipped; markdown-link fallback extracts title/url/snippet correctly; no links in text → `[]`; an overly long snippet is truncated; structured content is preferred over text content when both are present.
- ✅ **`searchKnowledge()`** (`src/lib/search/knowledge.ts`) — adds `microsoftDocs` as a sixth parallel call (`Promise.all`, alongside the other five), ranked last per the original Module 10 brief's ordering: Historical Projects → Playbooks → Lessons Learned/Incidents → Scripts → SOPs → Microsoft Docs. Deliberately last — this account's own real, internally-authored content outranks the one external, non-account-owned source, the same "real knowledge outranks…" rationale `searchVault` already documents for AI-generated content.
- ✅ **`/dashboard/search`** — new "Microsoft Docs" section, last, with three states: `null` → "Microsoft Docs search is unavailable right now — try again in a moment."; `[]` → "No matching Microsoft Docs articles."; results → a card per result linking out with a real `<a target="_blank">` (not a Next `<Link>` — these are external URLs), a "learn.microsoft.com" badge, title, and snippet.
- ✅ **UI verified via a throwaway preview route + Playwright**, screenshotted in both themes with three representative example results (DLP policies, retention labels, insider risk management) since the live endpoint is unreachable from this sandbox — card layout, badge, title/snippet wrapping, and external-link styling all render correctly and match the other five sections' established card shape; preview route deleted and a clean rebuild confirmed no leftover references.
- ✅ `npx tsc --noEmit` (via `npm run build`) / `eslint` / `npm run test` (218/218, 7 new) / `rm -rf .next && npm run build` all clean. No migration — no new database objects.
- **Not live-tested — genuinely, not just the usual caveat:** every other "not live-tested" note in this document is against an integration this session already proved works elsewhere in this codebase (AI generation, semantic search, email, Stripe) and is only blocked from a live round-trip by this sandbox's own network egress. This one is different: the Microsoft MCP endpoint has never been reached from anywhere in this session, so the response-shape assumptions in `parseMicrosoftDocsSearchResult()` — while written defensively against the two most likely shapes — are unconfirmed against the real server. Verify live in production after merge; if the real shape doesn't match either code path, the fallback returns `[]` (a wrong "no results," not a crash), and the fix would be narrowly scoped to `parseMicrosoftDocsSearchResult()` alone.
